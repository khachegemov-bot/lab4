# Лабораторная работа 4. Вариант 26 — Городские обращения о благоустройстве

REST API для приёма жалоб жителей на состояние городских объектов (дороги, парки, освещение…)
и организации ремонтных работ: обращение → наряд бригаде → работы → результат.

**Стек:** Java 21, Spring Boot 3.5.6, Spring Security 6, Spring Data JPA (Hibernate), PostgreSQL, Maven.

Задание 4 добавляет к API из задания 3 аутентификацию (HTTP Basic), защиту от CSRF,
регистрацию пользователей и авторизацию по ролям — см. раздел [«Аутентификация и авторизация»](#аутентификация-и-авторизация).

## Предметная модель

```
User (житель) 1 ──< N CityReport (обращение) N >── 1 CityObject (городской объект)
                              1
                              │
                              N
                       WorkOrder (наряд) N >── 1 WorkCrew (бригада) 1 ──< N типы объектов
```

| Сущность | Таблица | Что хранит |
|---|---|---|
| Пользователь | `users` | логин (уникален без учёта регистра), BCrypt-хеш пароля, роль, статус, счётчик неудачных входов, ФИО, email |
| Городской объект | `city_objects` | адрес, тип (`ROAD`, `PARK`, `LIGHTING`…), состояние |
| Обращение | `city_reports` | объект, автор, описание, статус, причина отклонения |
| Бригада | `work_crews` + `work_crew_supported_types` | название, какие типы объектов обслуживает, лимит активных работ |
| Наряд | `work_orders` | обращение, бригада, срок, статус, результат, время начала/завершения |

**Статусы**
- Обращение: `NEW` → `IN_PROGRESS` → `RESOLVED`, либо `REJECTED`.
- Наряд: `PLANNED` → `IN_PROGRESS` → `DONE`, либо `CANCELLED`. Активные — `PLANNED` и `IN_PROGRESS`.
- Объект: `GOOD`, `NEEDS_REPAIR`, `UNDER_REPAIR`, `DANGEROUS`.

## Бизнес-операции

Статусы меняются **только** этими операциями (через PATCH поменять статус нельзя — 400).
Каждая операция выполняется в одной транзакции: либо все изменения сохраняются, либо ни одно.

| # | Операция | Запрос | Что меняется | Когда запрещена (409/400) |
|---|---|---|---|---|
| 1 | Назначить бригаду на обращение | `POST /api/city-reports/{id}/assign` `{crewId, deadline}` | создаётся наряд `PLANNED`, обращение `NEW → IN_PROGRESS`, у бригады занимается место в лимите | обращение закрыто; у обращения уже есть активный наряд; бригада не обслуживает тип объекта; лимит бригады исчерпан; срок в прошлом |
| 2 | Начать работы | `POST /api/work-orders/{id}/start` | наряд `→ IN_PROGRESS`, объект `→ UNDER_REPAIR` | наряд не `PLANNED`; срок наряда истёк |
| 3 | Завершить работы | `POST /api/work-orders/{id}/complete` `{resultDescription}` | наряд `→ DONE`, обращение `→ RESOLVED`, объект `→ GOOD` (если других открытых жалоб нет) | наряд не `IN_PROGRESS` (сначала надо начать работы) |
| 4 | Отменить наряд | `POST /api/work-orders/{id}/cancel` | наряд `→ CANCELLED`, обращение `→ NEW`, объект `UNDER_REPAIR → NEEDS_REPAIR` | наряд уже закрыт |
| 5 | Передать наряд другой бригаде | `POST /api/work-orders/{id}/reassign` `{crewId}` | наряд переходит к новой бригаде: у старой место освобождается, у новой занимается | работы уже начаты; новая бригада не обслуживает тип объекта или её лимит исчерпан |
| 6 | Отклонить обращение | `POST /api/city-reports/{id}/reject` `{reason}` | обращение `→ REJECTED` с причиной, запланированный наряд отменяется, состояние объекта пересчитывается | обращение закрыто; по нему уже идут работы |

Дополнительные правила целостности:
- новое обращение на объект в состоянии `GOOD` переводит его в `NEEDS_REPAIR`;
- `UNDER_REPAIR` нельзя поставить или снять вручную — только операциями 2–4;
- нельзя сменить тип объекта, если над ним работает бригада, не поддерживающая новый тип;
- нельзя уменьшить лимит бригады ниже числа её активных работ или убрать тип, по которому есть активный наряд;
- выполненный наряд и бригаду с историей работ удалить нельзя;
- удаление пользователя или объекта каскадно удаляет их обращения и наряды.

## CRUD

Для `/api/users`, `/api/city-objects`, `/api/city-reports`, `/api/work-crews`, `/api/work-orders`:
`GET` (список), `GET /{id}`, `POST` (201), `PATCH /{id}` (200), `DELETE /{id}` (204).

## Аутентификация и авторизация

### Как войти

- **HTTP Basic:** логин и пароль передаются в заголовке `Authorization` каждого запроса. Сессий нет (`STATELESS`).
- **CSRF:** любой изменяющий запрос (`POST`, `PATCH`, `DELETE`) требует токен.
  1. `GET /api/csrf` (без входа) → `{"headerName":"X-XSRF-TOKEN","token":"..."}` и cookie `XSRF-TOKEN` (HttpOnly, SameSite=Strict).
  2. В изменяющих запросах — заголовок `X-XSRF-TOKEN: <token>` (cookie клиент отправляет сам).
  Без токена или с неверным токеном — **403**. При Basic-аутентификации CSRF актуален: браузер
  запоминает введённые учётные данные и подставляет их даже в запросы, отправленные чужой страницей.
- **CORS:** по умолчанию браузерные запросы с чужих сайтов запрещены (`app.cors.allowed-origins` пуст).

| Запрос | Кто | Что делает |
|---|---|---|
| `GET /api/csrf` | все | выдаёт CSRF-токен |
| `POST /api/auth/register` `{username, password, fullName, email}` | все (с CSRF) | регистрация жителя: роль всегда `RESIDENT` |
| `GET /api/auth/me` | вошедший | кто я, моя роль |
| `POST /api/auth/change-password` `{currentPassword, newPassword}` | вошедший | смена своего пароля |

### Учётные записи и пароли

- Пароли хранятся только как **BCrypt-хеш** (`BCryptPasswordEncoder`, cost 12). БД дополнительно
  проверяет формат (`CHECK`): пароль в открытом виде в таблицу не запишется. Хеш не возвращается в ответах API
  и недоступен пользователю БД `city_readonly`.
- **Надёжность пароля:** 8–64 символа (не больше 72 байт — предел BCrypt), есть буква и цифра, без пробелов,
  не содержит логин, не из списка распространённых паролей.
- **Уникальность логина** без учёта регистра: проверка в коде + уникальный индекс в БД → 409.
- **Повышение привилегий при регистрации невозможно:** в запросе нет поля `role`, а неизвестные поля JSON
  запрещены → `"role":"ADMIN"` даёт 400. Роль меняет только администратор.
- **Состояние учётной записи:**
  - `ACTIVE` / `BLOCKED` — блокирует администратор, заблокированный не может войти;
  - временная блокировка: после **5** неверных паролей подряд вход закрыт на **15 минут** (защита от перебора),
    снимается по времени или администратором (`status: ACTIVE`).
  - На любой сбой входа ответ одинаковый — **401** без уточнения причины: по ответу нельзя узнать,
    существует ли логин и заблокирован ли он.

Тестовые учётные записи (создаёт `db/03_seed.sql`, только для учебного стенда):

| Логин | Пароль | Роль | Статус |
|---|---|---|---|
| `admin` | `Admin#City2026` | ADMIN | ACTIVE |
| `dispatcher` | `Dispatch#2026` | DISPATCHER | ACTIVE |
| `ivanov` | `Ivanov#2026` | RESIDENT | ACTIVE |
| `petrova` | `Petrova#2026` | RESIDENT | ACTIVE |
| `sidorov` | `Sidorov#2026` | RESIDENT | BLOCKED |

### Роли и права

Роль — набор прав (authorities). В `@PreAuthorize` проверяются права, а не названия ролей.

| Право | RESIDENT (житель) | DISPATCHER (диспетчер) | ADMIN |
|---|:-:|:-:|:-:|
| `REPORT_CREATE` — подать обращение от своего имени | ✔ | ✔ | ✔ |
| `REPORT_CREATE_FOR_OTHERS` — от имени другого жителя | | ✔ | ✔ |
| `REPORT_READ_ALL` — видеть все обращения | | ✔ | ✔ |
| `REPORT_EDIT_ANY` — править любое открытое обращение | | ✔ | ✔ |
| `REPORT_DELETE_ANY` — удалять любое обращение | | | ✔ |
| `WORKFLOW_MANAGE` — наряды и бизнес-операции 1–6 | | ✔ | ✔ |
| `OBJECT_MANAGE` — создавать/менять объекты | | ✔ | ✔ |
| `OBJECT_DELETE` — удалять объекты | | | ✔ |
| `CREW_MANAGE` — бригады | | ✔ | ✔ |
| `USER_MANAGE` — пользователи, роли, блокировка | | | ✔ |

Читать справочники (объекты, бригады) может любой вошедший.

### Правила, зависящие от контекста операции

| Ситуация | Результат |
|---|---|
| Житель смотрит / меняет / удаляет **своё** обращение | разрешено (`@reportAccess`) |
| Житель обращается к **чужому** обращению (или к несуществующему id) | 403 — не раскрываем, есть ли такой id |
| Житель запрашивает список обращений | только свои |
| Житель подаёт обращение с чужим `authorId` | 403; без `authorId` автор — он сам |
| Автор правит или отзывает обращение после назначения бригады | 409 — бизнес-правило: только в статусе `NEW` |
| Пользователь смотрит / правит **свой** профиль (`#id == principal.id`) | разрешено; поля роли и статуса в запросе нет |
| Администратор меняет роль/статус **себе** или удаляет себя | 409 — нельзя остаться без администратора |

### Где задаются правила

- `SecurityFilterChain` (`security/SecurityConfig.java`) — правила по URL и методу; всё неперечисленное — `denyAll()`.
- `@PreAuthorize` на каждом методе контроллеров — точные правила, включая контекстные
  (`security/ReportAccess.java`).
- Бизнес-ограничения задания 3 (статусы, лимиты, переходы) остались в сервисах и работают для всех ролей.

### Ответы при отказе

Единый JSON `{timestamp, status, error, details}` без стек-трейсов и внутренних подробностей.

| Код | Когда |
|---|---|
| 401 | нет логина/пароля, неверный пароль, учётная запись заблокирована (+ заголовок `WWW-Authenticate: Basic`) |
| 403 | вошёл, но не хватает прав; отдельное сообщение — нет или неверен CSRF-токен |
| 409 | права есть, но операция нарушает бизнес-правило |
| 400 | неверные данные, слабый пароль, лишние поля (`role`, `id`, `status`) |

Неудачные входы, блокировки и отказы в доступе пишутся в лог сервера (без паролей; логин очищается от
управляющих символов — защита от подделки записей журнала).

## Безопасность (задание 3)

- **SQL-инъекции:** все запросы — через Spring Data JPA (методы репозиториев и JPQL с `:параметрами`),
  значения уходят в БД как параметры `PreparedStatement`, конкатенации SQL нет.
- **Секреты:** логин/пароль БД не хранятся в коде; они в файле `.env` (в `.gitignore`), образец — `.env.example`.
- **Минимальные права БД — три роли с разными привилегиями:**

  | Роль | Вход | Права | Для чего |
  |---|---|---|---|
  | `city_owner` | нет (`NOLOGIN`) | владелец схемы и таблиц: `CREATE`, `ALTER`, `DROP` | создание схемы администратором через `SET ROLE` |
  | `city_app` | да | `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицы схемы `city` | работа приложения |
  | `city_readonly` | да | только `SELECT`; в `users` — только `id`, `username`, `created_at` (ФИО и email закрыты); транзакции по умолчанию read-only | отчёты, аналитика, просмотр в pgAdmin |

  Ни одна из рабочих ролей не может удалить или изменить таблицы, сделать `TRUNCATE`,
  создать свои объекты или подставить свой `id`.
- **Целостность на уровне БД:** внешние ключи, `NOT NULL`, `UNIQUE`, `CHECK` (допустимые статусы,
  «выполненный наряд обязан иметь результат», лимит 1..100 и т. д.), частичный уникальный индекс
  «не более одного активного наряда на обращение». Даже при ошибке в коде БД не примет неверные данные.
- **Параллельные запросы:** строка бригады блокируется (`SELECT … FOR UPDATE`) при назначении наряда —
  лимит нельзя обойти одновременными запросами; `@Version` (оптимистичная блокировка) защищает от
  «потерянного обновления».
- **Ошибки:** единый JSON без стек-трейсов и текста ошибок PostgreSQL; нарушение ограничения БД → 409.
- **Mass assignment:** неизвестные поля в JSON → 400 (нельзя передать `id`, `status`, `createdAt`).

## Запуск (Windows)

1. Установить PostgreSQL (с Command Line Tools) и JDK 21. Maven ставить не нужно — в проекте есть Maven Wrapper (`mvnw.cmd`), он скачает Maven сам.
2. Создать БД, пользователей и тестовые данные (спросит пароль `postgres`, сам сгенерирует пароли и создаст `.env`).
   **После задания 3 скрипт нужно запустить заново** — в таблице `users` появились новые столбцы
   (данные будут пересозданы):
   ```
   powershell -ExecutionPolicy Bypass -File db\setup.ps1
   ```
   Вручную: `db/01_create_db_and_roles.sql` → `db/02_schema.sql` → `db/03_seed.sql`.
3. Запустить приложение из корня проекта: `.\mvnw.cmd spring-boot:run` (или Run в IntelliJ IDEA).
4. Импортировать в Postman `postman/city-reports.postman_collection.json` и запустить **Run collection**
   (136 запросов с автотестами). Папка 0 получает CSRF-токен, дальше — регистрация, вход, сценарии от имени
   жителя, диспетчера и администратора, успешные и неуспешные (401 / 403 / 409).

```
  model/       JPA-сущности и перечисления
  repository/  интерфейсы Spring Data JPA
  security/    SecurityConfig, загрузка пользователей, роли/права, проверки по автору, политика паролей,

  service/     CRUD-сервисы, WorkflowService (бизнес-операции), DomainStateSync (согласование статусов)
  controller/  REST-контроллеры (в т.ч. AuthController: CSRF, регистрация, вход, смена пароля)
  dto/         входные/выходные модели с валидацией
  exception/   единый обработчик ошибок
```
